# 应用安全方法与来源索引

本文件记录应用安全方案所采用的方法论依据、官方来源及使用边界。所有引用仅使用编号与自编摘要；标准原文版权归各自机构所有，不在此复制。客户须自行确认适用的标准版本与合规要求，本方案不代为推断。

## 1. 代码审计方法

### 1.1 分析路径

代码审计从**入口点**出发：HTTP 路由处理函数、消息队列消费者、定时任务、文件上传处理、反序列化点。沿数据流追踪到**危险操作**（SQL 执行、系统命令调用、文件读写、HTTP 外发、反射/序列化）之间的调用链，核查：

- **输入验证与编码**：用户可控数据在哪里进入、是否经过验证和适当编码后才到达危险操作。
- **认证与会话**：令牌签名与验证方式、会话生命周期管理、凭据存储（明文、弱哈希、可预测）。
- **访问控制/IDOR**：资源标识符来源、权限检查是否在数据层而非界面层执行、水平越权路径。
- **SSRF**：用户可控 URL 是否未经限制地发起服务端请求，目标是否可到达内网或元数据端点。
- **反序列化**：不可信数据经过何种反序列化机制，是否存在 gadget chain 可利用条件。
- **路径遍历**：文件路径拼接是否经过规范化，拼接后是否限制在允许目录内。
- **XSS（反射/存储/DOM）**：用户可控数据写入响应时是否经过上下文正确的编码。
- **密钥与配置**：硬编码凭据、弱随机数生成、调试模式、不安全的 TLS 配置。
- **依赖安全**：已知 CVE、许可证合规；版本锁定与 SCA 工具输出作为辅助证据。

每条发现须有：代码版本、文件路径、行号、入口点到危险操作的最短可达路径、利用前提条件（权限级别、可控参数、网络可达性）、影响（机密性/完整性/可用性）、CWE 编号（参照 MITRE CWE，固定使用访问日版本）、修复建议（最小变更）和验证方法（可运行测试或静态断言）。

### 1.2 置信度分级

| 级别 | 含义 | 条件 |
|---|---|---|
| 已确认 | 有完整静态调用链，无需动态运行即可证明可达 | 调用链中无不可分析的间接跳转或动态加载 |
| 疑似 | 有部分证据，存在不可静态确认的间接跳转或条件 | 需要动态运行或 DAST 补充验证 |
| 需运行验证 | 静态分析无法确定是否可达或可利用 | 反射调用、动态代码生成、框架魔术方法等 |

扫描器输出（SAST/SCA）默认标为「疑似」，需经人工路径核查后才可提升为「已确认」。

## 2. 安全设计评审方法

安全设计评审对照 OWASP ASVS 5.0.0（ASVS 5.0.0，2025-05，CC-BY-SA-4.0，
来源：[https://github.com/OWASP/ASVS](https://github.com/OWASP/ASVS)）章节编号核查设计证据。

**引用规则**：引用时仅使用条目编号（如 V2.1.1）与自编摘要，不复制标准原文。ASVS 许可为 CC-BY-SA-4.0，改编须按许可要求处理。

**评审步骤**：
1. 确认输入材料：PRD/架构图/API 契约、数据分类、身份与权限矩阵、第三方依赖清单、部署描述。
2. 列出适用的 ASVS 章节（V1 架构、V2 认证、V3 会话、V4 访问控制、V5 验证、V6 密码学、V7 错误处理、V8 数据保护、V9 通信、V10 恶意代码、V11 业务逻辑、V12 文件上传、V13 API、V14 配置）及排除理由。
3. 对每条适用要求，核对设计文档中的对应声明，区分：
   - **已满足**：有明确设计证据，且证据与声明阶段一致（设计图 ≠ 实现证据）
   - **有条件满足**：有部分证据，但有待补充约束或版本确认
   - **证据不足**：文档未提及或描述不清楚
   - **需整改**：有明确设计缺陷
4. 形成评审备忘录：每条结论附 ASVS 编号、证据引用、差距描述及建议责任人/期限。

**局限**：设计评审通过不等于实现正确；实现评审与部署验证是独立任务。

## 3. 威胁建模方法

基于 OWASP Threat Modeling Cheat Sheet（滚动更新，
来源：[https://cheatsheetseries.owasp.org/cheatsheets/Threat_Modeling_Cheat_Sheet.html](https://cheatsheetseries.owasp.org/cheatsheets/Threat_Modeling_Cheat_Sheet.html)）的四问框架：
系统是什么 → 什么可能出错 → 如何应对 → 是否充分。

**STRIDE 威胁分类**（对每个数据流/信任边界/进程应用）：
- **S（欺骗）**：身份冒充，认证绕过
- **T（篡改）**：数据完整性破坏
- **R（抵赖）**：操作可否被审计追溯
- **I（信息泄露）**：敏感数据暴露
- **D（拒绝服务）**：可用性影响
- **E（权限提升）**：绕过访问控制获取更高权限

**产出要素**：系统边界图（文本 DFD 或客户工具格式）、数据流清单（数据类型、传输路径、加密状态）、资产与主体清单、信任边界列表、STRIDE 威胁台账（威胁描述、受影响组件、可能性/影响、缓解措施、验证用例、残余风险、负责人）、假设清单（不在威胁模型范围内的前提）。

对包含 AI/Agent 组件的系统，可补充：工具越权（Agent 被诱导执行授权范围外操作）、提示注入（不可信数据改变 Agent 行为）、数据外传（Agent 将敏感数据写入外部端点）、执行回执信任（将 Agent 执行结果当作已核验事实）。这些场景需以实际架构为依据，不能仅凭组件名称断言。

## 4. 扫描结果复核方法

**输入类型**：SAST 报告（如 Semgrep CE、CodeQL SARIF）、SCA 报告（依赖漏洞）、DAST 报告（如 ZAP）、Secret 扫描输出。

复核步骤：
1. 去重：同一代码位置的多工具重复 finding 合并，保留最高置信度。
2. 误报判定：核查数据流路径是否实际可达、是否已有输入校验拦截，记录判定理由。
3. 优先级分类：综合 CVSS 基础分（仅作参考）、可达性、业务资产价值（需客户提供）、是否已有 KEV 记录（参照 CISA KEV 数据，来源：[https://github.com/cisagov/kev-data](https://github.com/cisagov/kev-data)）、修复难度，给出 P0–P3 建议优先级。
4. 标注未覆盖：列出构建失败目录、不支持的语言或框架、忽略规则及影响。

**局限**：CVSS 评分不单独决定处置优先级；KEV 未收录不等于无风险；SCA 报告的漏洞版本需结合实际调用路径判断是否可达。

## 5. Web 渗透测试协作方法

**参考**：OWASP WSTG v4.2（WSTG v4.2，稳定版，来源：[https://github.com/OWASP/wstg](https://github.com/OWASP/wstg)）；WSTG 5.0 仍在开发，引用须固定版本。

**协作范围**：本岗位交付「测试计划」和「发现整理」，**不执行主动测试**。主动测试（含 ZAP 主动扫描、模糊测试、漏洞利用验证）需单独授权范围与隔离环境，不在本岗位交付范围内。

**测试计划内容**：
- 授权确认清单：目标域名/IP/应用归属、授权书与批准人、测试环境与窗口、排除路径、禁止动作、停止联系人、证据保留规则。
- 按 WSTG v4.2 测试类别编号（如 WSTG-AUTHN-01、WSTG-AUTHZ-01 等）列出适用测试用例，说明测试方法、所需账号角色、预期证据形式。

**发现记录模板**：WSTG 测试编号、标题、严重程度、发现描述、请求/响应摘要（脱敏）、复现条件、业务影响、修复建议及验证方法。

**注意**：ZAP baseline 会启动爬虫并发送请求，仍需目标授权；ZAP 主动扫描进行攻击性测试，须单独授权。授权范围不明确时只交测试计划，不启动任何扫描或请求发送。

## 6. 修复验证方法

修复验证针对已记录的发现，核对修复版本：
1. 对照原发现的文件/行号，确认代码已按建议修改。
2. 对照原利用条件，确认修复是否完整覆盖所有入口（包括重复模式）。
3. 确认修复未引入新风险（如替换方案的安全属性）。
4. 如有测试用例，确认原先触发漏洞的测试通过、功能回归测试通过。
5. 对「疑似」或「需运行验证」的发现，修复验证不能仅凭静态分析闭环，须说明动态验证方式或残余不确定性。

产出：逐条发现的验证结论（已修复/部分修复/未修复/新引入问题），附证据文件路径与行号差异说明。
