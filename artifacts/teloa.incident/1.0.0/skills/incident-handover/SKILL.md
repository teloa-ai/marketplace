# 值班交接记录

> 复用自 teloa.soc 1.0.1 的 shift-handover 技能，按研发事件值班岗位改写：增加「临时缓解到期项」「下一班次计划变更与发布窗口」栏目；挂起动作明确为回滚、重启、变更等待确认；保留「不在交接中执行处置」「不写凭据」规则。

## 适用输入与前置检查

**必须提供：**
- 本班处理的事件与告警 ID 列表及当前状态（已上传或本次提供）
- 本班执行的关键动作记录（研判、建议、升级、暂停的排查）

**可选输入：**
- 尚未完成的排查说明
- 下一班次内的计划变更、发布窗口或维护计划
- 接班者标识（用于记录）
- 工具与连接的异常记录

**前置检查：**
1. 每个活跃事件的最新状态已在材料中有依据；无依据的写「状态不明，接班优先核查」。
2. 没有未列出的挂起动作；凡建议了回滚、重启、变更而尚未被确认执行的，都要列入「挂起的待确认动作」。

## 分步方法

### 第一步：活跃事件清单
- 列出本班所有事件与告警：ID、等级、当前状态（初判中 / 缓解中 / 观察中 / 已恢复待复盘 / 已关闭）、当前负责人（材料中的）
- 每个事件写一句「接班后最重要的下一步」

### 第二步：本班关键动作
- 只列关键动作：研判结论、提交的建议、升级、暂停的排查、被确认执行的变更（写出确认者与时间）
- 不列全部查询与查看

### 第三步：关注点与到期项
- 下班后可能变化的风险：告警频率上升的组件、接近阈值的容量、依赖方的已知问题
- **临时缓解到期项**：为缓解事件做的临时措施（调长缓存、关闭开关、临时扩容）及其预计需要回退或复查的时间
- 数据盲点：某监控或日志源不可用或延迟

### 第四步：下一班次计划变更与发布窗口
- 「下一班次」范围：材料给出接班班次起止时以材料为准；未给出时取本班结束起 24 小时，并在该节首行写明所取范围
- 列出材料中下一班次内的计划发布、变更窗口、维护
- 标出与活跃事件可能冲突的项，写「是否推迟由负责人决定」

### 第五步：工具与连接状态
- 记录本班发现的工具异常：错误追踪配额、监控面板延迟、告警渠道失效

### 第六步：挂起的待确认动作
- 每项写：事件 ID、建议动作、等待谁确认、提出时间
- 不隐含在「下一步」里

## 输出结构

```
# 值班交接记录

班次时间：[UTC 起止]（原时区：[起止]）
值班：[本班标识]
接班：[接班者 或「待分配」]
来源：[文件清单]

---

## 活跃事件状态
| 事件/告警 ID | 等级 | 当前状态 | 接班后最重要的下一步 | 负责人（原文） |
|---|---|---|---|---|

## 本班关键动作
| 时间（UTC / 原时区） | 动作 | 结果 | 来源 |
|---|---|---|---|

## 关注点与到期项
- [风险或盲点]
- 临时缓解到期：[措施 + 预计复查/回退时间 + 事件 ID]

## 下一班次计划变更与发布窗口
范围：[UTC 起止]（依据：接班班次起止 / 本班结束起 24 小时）
| 时间（UTC / 原时区） | 变更或发布 | 与活跃事件的关系 | 来源 |
|---|---|---|---|

## 工具与连接状态
- [工具]：[状态]

## 挂起的待确认动作
- [事件 ID] — [建议动作] — 等待：[确认者] — 提出于 [时间 UTC]
```

## 证据与引用规则

- 每个事件引用 ID 与材料来源，不凭记忆描述
- 已被确认执行的变更写出确认者与时间；未确认的一律进「挂起」
- 时间写 UTC 并括注原时区

## 未知/冲突/缺失怎么处理

- **状态无法确认**：写「状态不明，接班优先核查」
- **数据源班内中断后恢复**：记录中断时段，供接班评估证据缺口
- **接班者未定**：写「待分配」

## 何时停下找人

- 存在等级 P1/P2 的活跃事件且没有明确负责人
- 临时缓解到期时间落在本班结束前但尚无人确认如何处理

## 禁止事项

- 不在交接记录中执行或触发任何处置动作
- 不省略挂起的待确认动作
- 不写入凭据、令牌或外部系统账号
- 不对任何个人作评价
