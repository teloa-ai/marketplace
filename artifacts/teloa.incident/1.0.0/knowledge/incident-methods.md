# 研发事件响应方法与来源索引

## 适用范围

本文档适用于事件值班协作员的四类典型任务：事件分级与初判（含缓解变更说明草案）、事件时间线、无责复盘报告、值班交接记录。所有方法以已获准的本地材料为起点，不依赖错误追踪、告警平台或代码托管的实时连接；连接为可选项，接入后仍按同一规则处理。

## 一、共同原则

1. **时间双列**：每个时间写 UTC 并括注原时区；时间差由两个已列出的时间相减得到，读者可复算。
2. **事实、推断、待确认分开**：材料证实的写事实；从时间相关性得出的写「疑似」；材料无法证实的写「待确认」。
3. **只出建议不执行**：回滚、重启、扩容、开关、配置变更由授权人员执行；岗位只出描述性说明，不生成可直接执行的命令。
4. **不对外**：状态页、事故公告、客户沟通由负责人决定并执行；岗位不起草面向客户的通告。
5. **无责**：原因归到系统、流程、工具与信息流；不出现对个人的归责、评价或处分建议。
6. **不读未提供的系统**：不主动访问生产环境、代码仓库、监控或聊天记录。

## 二、事件分级与初判

判定三选一：确认事件 / 已解释的正常波动 / 待定。等级按组织规则逐条对照，未提供规则时用默认表并在首部注明：

| 等级 | 条件（满足任一） |
|---|---|
| P1 | 核心功能不可用；核心链路错误率 >5% 持续 >10 分钟；数据丢失、资金错误或安全泄露风险 |
| P2 | 核心功能降级有绕行；核心链路错误率 2–5%；非核心功能不可用 |
| P3 | 非核心功能降级；影响单个客户或内部用户 |
| P4 | 无用户影响的异常 |

分级条件有材料无法证实的部分时，按已证实部分给等级并注明未证实条件；两级之间无法判定时取较高等级标「待确认」。

疑似关联变更：列出异常开始前 24 小时内的部署、配置、开关与基础设施变更，写出与首个异常迹象的时间差、是否在错误路径上；只标「疑似」。

## 三、缓解变更与回滚说明

回滚目标必须可识别（标签、提交号、发布 ID、配置旧值）。版本差异未提供时影响范围写「变更内容待确认」。风险表必须包含「目标版本与当前版本之间是否有数据库迁移或数据格式变化」一项。执行步骤描述性，验证步骤引用触发事件的告警阈值，附「变更本身失败时的回退」。待填写字段（审批人、变更窗口、工单 ID、执行人与时间、验证结果）不可省略。

## 四、事件时间线

五个关键节点：异常开始（最早异常迹象）、检测（告警触发或首次报告）、响应（首位处理者接手）、缓解（使影响停止扩大的动作完成）、恢复（指标回到正常或告警解除）。

四个用时：检测用时 = 检测 − 异常开始；响应用时 = 响应 − 检测；缓解用时 = 缓解 − 异常开始；总持续时长 = 恢复 − 异常开始。缺节点则写「无法计算」。

可信度：High（原始日志、部署系统记录、告警系统事件）、Medium（聚合指标、面板说明、工单字段）、Low（群消息口头描述、事后回忆）。缺口只标注，不用推断填补。

## 五、无责复盘

原因分三层：触发条件（直接导致异常开始的事件）、直接原因（系统为何在触发后产生影响）、促成因素（触发为何得以发生、检测与缓解为何耗时）。状态只有「已确认」（材料明确说明已验证）与「最可能（待验证）」。

报告包含：做得好的地方（有时间线依据）、运气因素（条件不同影响会更大的事实）、改进行动建议（具体可验证，与促成因素一一对应，负责人与期限只取材料原文）、未完成事项、无责声明。

材料中出现对个人的归责表述时不写入报告，标注由负责人决定。

## 六、值班交接

活跃事件每条写「接班后最重要的下一步」。凡建议了回滚、重启、变更而尚未被确认执行的动作都列入「挂起的待确认动作」。临时缓解（调长缓存、关闭开关、临时扩容）写预计复查或回退时间。下一班次内的计划发布与变更窗口标出与活跃事件的关系，「是否推迟由负责人决定」。不写凭据。
