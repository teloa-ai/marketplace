# 调查假设与验证计划（Investigation Hypothesis and Verification Plan）

## 适用输入与前置检查

必须提供：
- T1 研判卡或已整理的初始证据摘要
- 已知实体列表（主机、账号、IP 等）

可选：
- 初步证据时间线
- 已知资产分级与业务上下文
- 客户响应手册（若有，提供对本场景适用的部分）

前置检查：
1. 假设必须来自现有证据，不能无中生有。
2. 每个假设必须是可证伪的：需要说明什么样的证据会推翻它。
3. 若现有证据极少，应先生成"证据收集计划"而非过多假设。

## 分步方法

**步骤 1 — 明确已知事实**
- 列出已被证据支撑的事实（不含推断）。
- 列出已知的"缺口"（需要回答的关键问题）。

**步骤 2 — 生成假设**
- 为每个关键缺口生成 1–3 个可证伪的假设。
- 假设格式："[攻击者/事件原因] 通过 [方法] 对 [资产] 实施了 [目的]，证据应体现在 [数据源] 中"。
- 同时生成替代假设（包括良性解释）：不能只构建支持威胁的假设。
- 标注每个假设与 MITRE ATT&CK v19.x 技术的对应关系（如适用）。

**步骤 3 — 优先级排序**
- 按以下标准为假设排优先级：
  - 对资产影响严重程度（高影响先验证）
  - 现有证据支持强度（已有部分证据的先验证）
  - 验证所需数据的可及性（数据已有的先验证）

**步骤 4 — 制定验证步骤**
- 为每个假设列出验证步骤：
  - 需要查询的数据源（SIEM、EDR、目录服务等）
  - 具体查询逻辑或字段（不写平台特定语法，写逻辑描述）
  - 预期的正面证据（支持假设）
  - 预期的反面证据（推翻假设）
  - 所需授权（若某步骤需要额外权限，标注）

**步骤 5 — 识别排除标准**
- 对每个假设说明：如果找到什么证据，可以合理排除该假设。
- "排除"不等于"无威胁"，排除某假设后需说明转向哪个替代假设。

## 输出结构

```
## 已知事实（证据支撑）
1. [事实描述] — 来源: [数据来源]
2. ...

## 关键缺口（待回答问题）
1. [问题描述]
2. ...

## 假设与验证计划

### 假设 H1（优先级：High/Medium/Low）
**陈述**: [假设描述]
**ATT&CK 对应**: [技术编号 技术名称（v版本）] 或"暂无对应"
**支持证据**: [已有的支持性证据摘要]
**验证步骤**:
- 步骤 1: [数据源] — [查询逻辑描述] — 预期正面证据: [...] / 反面证据: [...]
- 步骤 2: ...
**排除标准**: 若找到 [具体证据]，可排除本假设。
**所需额外授权**: [无 / 具体说明]

### 假设 H2（替代/良性解释）
...

## 验证优先顺序
1. H[N] — 理由
2. ...

## 建议数据收集
若以下数据已获授权，可显著提升调查效率：
- [数据源]: [具体用途]
```

## 证据与引用规则

- 每个假设的"支持证据"必须引用已在证据时间线或实体清单中出现的条目，不引用外部推断。
- ATT&CK 技术编号必须带版本（如 `T1078（ATT&CK v19）`），不使用不带版本的编号。
- "替代/良性解释"假设不是敷衍，必须认真构建并验证。

## 未知/冲突/缺失处理

- 现有证据支持两个相互排斥的假设：保留两者，各自制定验证步骤，不提前选择。
- 所有数据源均无相关数据：标注为"数据盲点"，将收集数据的步骤作为首要任务。
- 客户提供的背景信息与证据矛盾：列出矛盾，不自行裁决。

## 禁止事项

- 不得只生成支持威胁的假设，必须包含良性替代解释。
- 不得在验证步骤中写平台特定查询语句（应由平台转换技能或用户自行翻译）。
- 不得将未验证假设写入事件报告的"根因"字段。
- 不得建议未经授权的主动验证（如主动探测目标主机或外发请求）。
