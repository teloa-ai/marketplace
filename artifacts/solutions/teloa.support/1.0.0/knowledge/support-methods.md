# 客户支持方法与来源索引

## 适用范围

本文档适用于客服知识协作员的四类典型任务：工单分诊、客户回复草案、FAQ 沉淀、回复事实与措辞核对。所有方法以已获准的本地材料（工单、事实库、政策、既有 FAQ）为起点，不依赖工单系统或即时通讯的实时连接；连接为可选项，接入后仍按同一规则处理。

## 一、共同原则

1. **事实有出处**：对客户说的每个事实来自产品事实库或支持政策的具体条目；找不到就写「待确认」，不以常识、经验或网络信息补齐。
2. **岗位不做承诺**：退款、赔偿、补偿、折扣、延期、例外处理、修复时间、上线日期，一律不在草案中给结论；统一写「已记录，将由负责人评估」。
3. **个人信息最少化**：客户姓名、联系方式、账号、订单号、地址、支付信息只在单条工单处理内部引用；分诊表、升级摘要、FAQ 中只保留工单编号；引用客户原话时遮蔽这些字段。
4. **先分诊再动笔**：只有处理路径为「一线回复」的工单才起草对外文字；升级类只出摘要。
5. **发送前必经核对**：回复草案与 FAQ 条目在交负责人前过一次事实与措辞核对（三类结论：已核实 / 待确认 / 存疑）。
6. **组织规则优先**：组织提供了分类体系、优先级定义、SLA、话术或禁用表述清单时以组织为准，并在输出首部注明采用的规则；未提供时用本方案默认规则并注明。

## 二、工单分诊

默认问题类型：使用咨询、账户与登录、订单与支付、故障报告、数据与隐私、功能建议、投诉与升级、其他。一条工单多个问题拆行。

优先级四档（写依据）：
- **P1**：支付异常、账户被盗、数据泄露、安全事件、多用户不可用、客户提及法律/监管/媒体/人身安全 → 停止起草，交负责人
- **P2**：核心功能不可用且无绕行；要求赔偿的投诉；政策定义的重点客户
- **P3**：有绕行方案的异常；订单支付非异常类；重复咨询
- **P4**：使用咨询、功能建议、可自助

处理路径：自助（给出 FAQ/事实库位置）/ 一线回复 / 升级（P1 全部；退款赔偿补偿；事实库无答案或冲突；疑似故障无已知记录；情绪危机或威胁；政策要求）。

批量时按「同一功能 + 同一现象」聚类；同簇 ≥3 条或短时集中即「疑似共性问题」，建议升级产品团队。

## 三、回复草案

结构：称呼 → 复述理解到的问题 → 逐条回答（步骤用编号列表）→ 未能回答的点与下一步 → 结尾。
语气：具体、直接、不推责、不过度道歉。长度：聊天 ≤150 字/条，邮件 ≤300 字。
随草案交付「依据表」（每条表述的来源位置）与「待确认项」（无条目 / 条目冲突 / 涉及承诺）。

## 四、FAQ 沉淀

流程：聚类（<2 次不入库）→ 抽取候选答案 → 每个事实点核对到事实库/政策（对不上的不入正文）→ 起草条目（问题、适用范围、简答、步骤、变体、相关条目、来源、核对日期）→ 与既有 FAQ 比对（重复 / 冲突 / 过期）→ 去个人信息与自检。
不写「通常」「一般」「应该」；不写客户没问过的内容；不修改既有 FAQ，只提建议。

## 五、事实与措辞核对

核对对象：产品事实、政策引用、承诺性表述、原因判断、对比评价、链接、个人信息、是否答非所问。
三类结论：已核实（有精确引用）/ 待确认（无对应条目）/ 存疑（不一致、超出政策的承诺、触发禁用表述、多余个人信息）。
所有存疑项与涉及承诺的待确认项列入「发送/发布前必须处理」。
