# 代码评审方法与来源索引

## 适用范围

本文档适用于代码评审协作员的五类典型任务：PR 评审、发布说明、Issue 分诊、安全修复验证、安全设计评审。所有方法以已获准的本地材料（差异、提交记录、Issue 文本、设计文档）为起点，不依赖代码托管平台或工单系统的实时连接；连接为可选项，接入后仍按同一规则处理。

## 一、共同原则

1. **只出草案**：评审意见、发布说明、追问都是给负责人的草案；在 PR 或 Issue 上发表、批准、合并、推送、发版、关闭由负责人确认后自行操作。
2. **每条意见有位置**：文件路径与行号（差异新版本行号）、提交或 PR 编号、Issue 原文片段，读者可以直接定位。
3. **区分阻断与建议**：阻断只用于错误结果、数据损坏、安全缺陷、关键路径无测试、未声明的不兼容变更、凭据入库；风格与偏好一律建议。
4. **不推断差异之外的行为**：看不到的调用方、配置或运行时行为写「提问」或「需人工复核」，不假设。
5. **不评价人**：意见针对代码与文本，不写作者个人评价、绩效或责任归因。
6. **凭据与恶意逻辑即停**：差异或 Issue 中出现密钥、令牌、凭据、个人敏感数据或疑似后门，标阻断并报告负责人，不复制其值、不给修复建议。
7. **不运行**：不运行差异中的代码、测试、脚本，不安装依赖；测试结论只来自差异中的测试文件与已提供的 CI 结果。

## 二、PR 评审

四个维度：正确性（边界、错误处理、逻辑、类型单位、调用方同步）、测试（新行为有测试、缺陷有回归测试、断言了关键结果、覆盖新分支）、安全（输入校验、认证授权、凭据与日志、依赖变更、路径/SQL/命令拼接）、可维护性（命名职责、重复、接口文档、死代码与调试残留、不兼容变更声明）。

三档：阻断 / 建议 / 提问；拿不准归提问。

结论三种：建议批准（无阻断）/ 建议请求变更（≥1 阻断）/ 需人工复核（差异不完整、版本未固定、描述与差异不一致、陌生领域）。

改动地图先于意见：先对照 PR 描述与实际改动，不一致处单列。

## 三、发布说明

归类七种且只归一类：不兼容变更（单列在前，附升级步骤）、安全（只写影响与升级建议）、新增、变更、修复（写现象不写实现）、弃用（附替代）、移除。

每条附来源编号；同一功能多条提交合并为一条并记录被合并编号；纯内部条目（CI、格式化、测试重构）移到「不写入说明的条目」表供核对；回滚与被回滚配对移出。

提交信息无行为依据（「修复若干问题」）写「需作者补充」，不编造。版本号与变更性质不相称列入「需负责人决策」，不自行改版本号。

## 四、Issue 分诊

类型五种：缺陷 / 功能请求 / 提问 / 文档 / 无法判定。信息完整度按类型核对（缺陷：版本、复现、预期与实际、环境、日志）。

优先级默认四档（团队定义优先）：P0 数据丢失、安全漏洞、核心功能全体不可用；P1 核心功能部分不可用无绕过；P2 有绕过的缺陷、明确功能请求；P3 体验、文档、提问。影响范围未说明降一档并注明。

查重只写「疑似重复于 #」与理由，不合并。追问只列缺失项，不承诺修复时间或版本。安全漏洞 Issue 不在公开分诊表展开复现细节。

## 五、安全修复验证与安全设计评审

见对应技能文件；两者从 teloa.appsec 复用，方法不变，增加了与 PR 评审结论的衔接：修复验证中任一「未修复 / 部分修复 / 新引入问题」对应 PR 阻断项，全部已修复但动态验证待安排对应「需人工复核」；设计评审中「需整改」对应阻断项，「证据不足」对应提问。
