# 修复验证（Fix Verification）

## 适用输入与前置检查

**必须提供：**
- 原始发现报告（含发现 ID、文件路径与行号、漏洞类别、利用条件）
- 修复后的代码快照（须固定版本/提交哈希）
- 修复说明（变更描述或 PR 描述，可选）

**可选提供：**
- 修复前代码快照（用于 diff 对比）
- 测试用例（单元测试、集成测试或渗透测试报告）
- 扫描工具对修复版本的重新扫描输出

**前置检查：**
1. 确认修复版本已固定（提交哈希或版本号）；未固定版本的验证结论不可追踪。
2. 确认原始发现 ID 与修复版本的对应关系已建立；否则无法闭环。
3. 确认未逾越授权范围（不执行主动测试、不推送代码）。

## 分步方法

**步骤 1：逐条核对代码变更**
- 对照原发现的文件路径与行号，在修复版本中定位对应代码。
- 检查是否已按发现中的修复建议方向修改（如参数化查询替代字符串拼接）。

**步骤 2：核查覆盖完整性**
- 检查是否存在相同模式的其他代码位置未被修复（例如同一函数在多个调用点均有风险，但只修了一处）。
- 核查修复是否覆盖原发现中所有入口点（若有多个入口点触发同一漏洞）。

**步骤 3：检查修复是否引入新风险**
- 修复替换的方案是否本身存在安全问题（如从弱加密替换为另一个弱加密）。
- 修复是否改变了数据流，从而影响其他功能的安全边界。

**步骤 4：评估动态验证需求**
- 对原置信度为「疑似」或「需运行验证」的发现，静态核查不能单独闭环，须说明动态验证方式（由负责人安排）。
- 若有测试用例或扫描重测报告，记录测试结果。

## 输出结构

### 验证摘要
- 修复版本标识（提交/版本号）
- 核查的发现总数
- 已修复 / 部分修复 / 未修复 / 新引入问题 统计

### 逐条验证记录

| 字段 | 说明 |
|---|---|
| 原始发现 ID | 对应原审计报告 ID |
| 验证结论 | 已修复 / 部分修复 / 未修复 / 新引入问题 |
| 修复版本中的代码位置 | 文件路径与行号 |
| 变更摘要 | 实际代码变更描述 |
| 覆盖完整性 | 是否有相同模式的遗漏位置 |
| 新引入风险 | 如有，描述新发现 |
| 动态验证状态 | 已完成 / 待安排 / 不适用，附测试结论或说明 |
| 残余不确定性 | 静态核查无法确认的部分 |

## 证据与引用规则

- 每条验证结论须有修复版本中的具体代码位置引用。
- 「已修复」结论须同时说明原入口点和原利用条件均已被覆盖，不仅仅是代码位置已修改。

## 未知/冲突/缺失的处理

- **修复版本未包含对应文件**：标注为「未修复」，不假设在其他地方处理。
- **修复说明与实际代码不一致**：以实际代码为准，在记录中注明差异。
- **动态验证结果与静态核查结论不一致**：记录冲突，升级到安全负责人。

## 禁止事项

- 不将「代码已修改」等同于「漏洞已修复」；须核查修复方向的正确性。
- 不执行任何测试代码或 PoC。
- 不推送修复代码到仓库；代码提交须由开发人员操作。
- 不在动态验证未完成时将「需运行验证」类发现标为「已修复」。
