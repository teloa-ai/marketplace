# 控制映射

## 概述

将组织的现有策略、技术控制和管理措施与一个或多个合规框架进行系统性对照，判定每项框架控制的满足状态，输出可用于审计准备和差距分析的映射表草案。

## 前置条件

执行控制映射前，需要以下材料：

- 目标框架版本（ISO 27001:2022、NIST CSF 2.0、SOC 2 TSC 2017、等保 2.0 等）
- 已有的安全策略或程序文件（已提供的版本）
- 现有控制清单（如有）
- 系统或业务范围说明

## 映射步骤

### 第一步：范围与框架确认

1. 确认适用框架和版本，记录框架来源（如"NIST CSF 2.0，2024 年版"）
2. 确认映射范围（全量控制 vs. 子集）
3. 记录假设（如"以下默认策略文件覆盖范围为全公司"）

### 第二步：控制清单整理

按框架结构逐条列出适用控制：

- **ISO 27001:2022**：附件 A 共 93 项，分 A.5（组织）、A.6（人员）、A.7（物理）、A.8（技术）四域
- **NIST CSF 2.0**：六个功能（GV/ID/PR/DE/RS/RC），每功能下若干类别和子类别
- **SOC 2 TSC**：通用标准 CC1–CC9，加可选标准（可用性 A、机密性 C 等）
- **等保 2.0**：分技术要求和管理要求，按二、三、四级分档

### 第三步：证据匹配

对每项控制，在已提供材料中检索对应证据：

- **完全匹配**：策略文件明确覆盖该控制，并有实施记录
- **部分匹配**：策略存在但缺少实施证据，或覆盖范围不完整
- **无匹配**：未找到对应的策略、程序或技术措施

### 第四步：状态判定

| 状态 | 标准 | 符号 |
|---|---|---|
| 已满足 | 有充分证据（策略文件 + 实施记录或配置截图）| ✓ |
| 部分满足 | 有策略但无实施证据，或覆盖不完整 | △ |
| 未满足 | 无策略或无任何证据 | ✗ |
| 不适用 | 控制明确不在系统/业务范围内（须说明原因）| N/A |

### 第五步：输出映射表

映射表字段：

| 控制编号 | 控制名称（自编摘要）| 状态 | 证据引用 | 缺口说明 | 备注 |
|---|---|---|---|---|---|

## 输出结构

### 映射摘要

```
框架：[框架名称和版本]
映射日期：[日期]
状态统计：
  已满足：X 项（Y%）
  部分满足：X 项（Y%）
  未满足：X 项（Y%）
  不适用：X 项（Y%）
整体合规覆盖率（已满足/适用总数）：Z%
```

### 映射明细表

按框架域逐项输出，每条记录包含：
- 控制编号（如 A.5.1、CC6.1）
- 控制名称（自编摘要，非原文）
- 状态（✓/△/✗/N/A）
- 证据引用（文件名/章节编号，或"未提供"）
- 缺口说明（部分满足或未满足时必填）
- 备注（假设或不确定性说明）

### 草案标注

映射表草案首行必须注明：
> 草案，待审阅确认后方可使用。以下证据引用基于本次提供的材料，实际控制实施状态需由负责人核实。

## 质量要求

- 每条控制编号引用须注明框架版本（如"NIST CSF 2.0"）
- 不录入框架标准原文，仅使用自编摘要描述控制内容
- 状态判定基于提供的材料，不做超出材料的推断
- 部分满足和未满足的条目必须写明具体缺口
- 不确定的状态标注"需核实"而非强行判定
- 多框架交叉映射时，标注各框架之间的对应关系

## 局限说明

- 本技能基于已提供的静态文档，不代表实际系统状态
- 控制实施效果需通过访谈、测试或独立审计验证
- 自动化工具配置状态需提供截图或导出记录才能判断
- 本技能不替代正式的合规评估或审计结论
