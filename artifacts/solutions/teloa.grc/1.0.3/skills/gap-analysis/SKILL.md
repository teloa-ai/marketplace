# 差距分析与整改计划

## 概述

差距分析将控制映射中"部分满足"和"未满足"的项目汇总，评估每项差距的风险影响，输出优先级排序的整改计划草案。整改计划草案供负责人审阅后确认责任人和完成日期。

## 前置条件

- 已完成的控制映射表（含状态和证据引用）
- 业务背景说明（用于评估差距的业务影响）
- 资产重要性信息（如有）

## 差距分类

### 按性质分类

| 类型 | 描述 |
|---|---|
| 策略缺失 | 相关策略或程序文件不存在 |
| 实施缺失 | 策略存在但未实施或无实施证据 |
| 证据缺失 | 控制已实施但无书面证明 |
| 范围不足 | 控制仅覆盖部分系统或场景 |
| 时效失效 | 证据已过期，控制状态不确定 |

### 按风险级别分类

- **高**：直接影响核心业务系统或敏感数据，缺失控制可能导致重大安全事件或审计不通过
- **中**：间接影响，缺失控制增加风险敞口，但有其他控制提供部分缓解
- **低**：影响有限，缺失控制属于流程完善性问题

## 分析步骤

### 第一步：差距汇总

从控制映射表中提取所有状态为"部分满足"和"未满足"的条目：

```
差距 ID：GAP-001
控制编号：ISO 27001:2022 A.8.8
控制摘要：技术漏洞管理——定期识别和修复技术漏洞
映射状态：未满足
缺口说明：未提供漏洞扫描报告或漏洞管理流程文档
```

### 第二步：风险影响评估

对每条差距评估：
1. **可能性**（1–5）：差距被利用的可能性（考虑威胁来源、控制缺失程度）
2. **影响**（1–5）：被利用后的业务影响（考虑资产重要性、数据敏感性）
3. **风险评分** = 可能性 × 影响
4. **风险级别**：≥15 高、8–14 中、<8 低

### 第三步：整改措施起草

对每条差距提供整改措施建议：

```
差距 ID：GAP-001
整改类型：技术+管理
整改措施：
  1. 部署漏洞扫描工具（如 Nessus、Qualys 或同类工具），覆盖所有范围内系统
  2. 制定漏洞管理程序，规定扫描频率（建议每月一次），以及 P1/P2/P3 漏洞修复时限
  3. 建立漏洞跟踪台账，记录发现日期、修复状态和责任人
建议负责人：[待负责人确认]
预计完成时间：[待负责人确认]
验收标准：有最近一次完整扫描报告，高危漏洞已修复或有例外记录
```

### 第四步：优先级排序

按风险评分降序排列差距，高风险差距优先列出。同等风险评分时，框架强制要求项优先于最佳实践项。

### 第五步：整改计划汇总

```
整改计划摘要
差距总数：X 项
  高风险：X 项（建议 30 天内启动）
  中风险：X 项（建议 60 天内启动）
  低风险：X 项（建议 90 天内启动）
```

## 输出结构

### 差距分析报告草案

**报告摘要**
- 分析框架和范围
- 差距总数和风险分布
- 最高优先级差距（前 3 项）

**差距明细表**

| 差距 ID | 控制编号 | 控制摘要 | 差距类型 | 可能性 | 影响 | 风险评分 | 风险级别 | 整改措施摘要 |
|---|---|---|---|---|---|---|---|---|

**整改计划表**

| 差距 ID | 整改措施 | 建议负责人（占位）| 建议完成日期（占位）| 验收标准 |
|---|---|---|---|---|

## 草案标注

报告首行必须注明：
> 草案，待审阅确认后方可使用。风险评分基于提供的材料和一般业务背景，需由负责人结合实际业务情况核实后调整。整改计划中责任人和完成日期为占位，须由负责人确认。

## 局限说明

- 风险评分依赖提供的业务背景，实际风险可能因系统重要性和攻击面而有所不同
- 整改措施为建议性，实际实施方案需由技术团队评估可行性
- 不包含对现有控制有效性的独立验证（有效性验证需通过测试或审计）
- 整改完成后需更新控制映射表和证据索引
